# Energy Dashboard – Scenario Comparison

A full-stack web application for visualizing energy consumption and PV (photovoltaic) generation, with an interactive scenario configuration that lets you compare baseline vs. custom PV capacity setups in real time.

![Dashboard Preview](./public/dashboard-preview.png)

---

## Branches

The project has one main line and two feature branches. Both feature branches start from `main` and are independent of each other.

| Branch | What it adds |
| ------ | ------------ |
| `main` | The dashboard: React frontend + Express/Prisma backend + PostgreSQL |
| `migration/express-to-fastapi` | A **Python FastAPI backend** (`server-py/`), a 1:1 port of the Express API. The frontend works unchanged with either backend. See [Python backend (FastAPI)](#python-backend-fastapi). |
| `feature/ai-agent-integration` | An **AI assistant** (chat panel + PV optimizer) powered by Groq / Llama 3.3 70B, running in the Express backend. See [AI Agent](#ai-agent-chat--optimizer). |

Switch branches with `git switch <branch>`, then reinstall dependencies if `package.json` changed (`npm install` in the root and in `server/`).

---

## Features

**All branches**

- **Time-series chart** — hourly baseline vs. scenario comparison for consumption and PV generation over a 7-day window, with a brush/zoom control
- **KPI cards** — live-recalculated total consumption (kWh), PV coverage (%), and CO₂ savings (t)
- **PV Configuration** — slider + numeric input (0–100 kW) to adjust PV capacity; changes are applied on demand
- **Save scenarios** — persist named scenarios via the API (in-memory, resets on restart); optimistic UI updates
- **Skeleton loading states & error boundaries** — graceful handling of slow or failed API calls

**`migration/express-to-fastapi`**

- **Second backend in Python** — FastAPI + psycopg with the same endpoints, JSON responses and error messages as Express
- **Interactive API docs** — generated by FastAPI at `/docs` (Swagger UI) and `/redoc`
- **Typed request validation** — Pydantic models mirror `shared/types.ts`; invalid bodies return `400 { "error": ... }`
- **pytest test suite** for the Python backend

**`feature/ai-agent-integration`**

- **AI Assistant (Groq + Llama 3.3 70B)** — tool-calling chat agent that can query the dataset, run what-if scenarios, and search for the optimal PV size
- **PV optimizer** — deterministic grid search for the best PV capacity by CO₂ savings, coverage, or consumption
- **Shared scenario store** — scenarios saved by the agent appear in the dashboard's saved list, and vice versa

## Backend Architecture

The Express backend follows a clear **separation of concerns** between two files:

| File | Responsibility |
| ---- | -------------- |
| `server/src/index.ts` | **Infrastructure** — creates the Express app, configures middleware (CORS, JSON parsing), sets the port, mounts routers, and starts the server |
| `server/src/routes/energy.ts` | **Application logic** — defines all route handlers, validates request data, reads from / writes to the database |

This separation means `index.ts` never contains business logic, and `energy.ts` never concerns itself with how the server is started or configured. Adding a new feature only requires creating a new router file and registering it in `index.ts` with a single `app.use(...)` line.

The FastAPI backend keeps everything in one file, `server-py/main.py`, with the same endpoints.

## Seeding the Database

The seed script (`server/prisma/seed.ts`) populates the `EnergyDataset` table with one week of mock hourly data (Jan 1–7, 2025) sourced from `mock-data/energy-2025-01-01-2025-01-07.json`.

Start the database and run the seed once after applying migrations. Both backends read the same database, so this is needed for FastAPI too.

```bash
docker compose up -d db
cd server
npm run db:migrate   # apply schema migrations
npm run db:seed      # load mock data into the database
```

**What it does:**
1. Reads the mock JSON file containing `timestamps`, `baseline`, `scenario`, and `kpis` arrays.
2. Clears any existing rows in `EnergyDataset` (safe to re-run).
3. Inserts a single `demo` dataset row that the `GET /api/energy` endpoint serves to the frontend.

> Without seeding, the `GET /api/energy` endpoint returns a `404` and the dashboard will show no data.

## Running the App: Express or FastAPI

The browser always talks to the Vite dev server (`http://localhost:5173`). Vite forwards every `/api` request to **one** backend, set by the proxy `target` in `vite.config.ts`:

| Backend | Port | Proxy target |
| ------- | ---- | ------------ |
| Express (`server/`) | 4000 | `http://localhost:4000` |
| FastAPI (`server-py/`, `migration/express-to-fastapi` only) | 8000 | `http://localhost:8000` |

Restart Vite after changing the target. Each backend keeps its own in-memory saved scenarios.

**With Express**

```bash
npm run dev          # starts Vite + Express together
```

**With FastAPI** (two terminals; see the next section for the one-time Python setup)

```bash
cd server-py && source .venv/bin/activate && uvicorn main:app --reload
```
```bash
npm run dev:web      # starts only Vite
```

> `npm run dev` always starts Express. When the proxy points to FastAPI, use `npm run dev:web` instead.

## Python backend (FastAPI)

*Branch: `migration/express-to-fastapi`*

`server-py/` is a 1:1 port of the Express API to Python (FastAPI + psycopg): same endpoints, same JSON responses, same error messages, so the React frontend works without changes.

**Prerequisites:** Python 3.9+, and PostgreSQL running and seeded (see [Seeding the Database](#seeding-the-database)).

**Mac / Linux**

```bash
cd server-py
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload        # http://localhost:8000
pytest                           # run the tests
```

**Windows (PowerShell)**

```powershell
cd server-py
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn main:app --reload        # http://localhost:8000
pytest                           # run the tests
```

The virtual environment only needs to be created once; after that, activate it in each new terminal (`source .venv/bin/activate` or `.venv\Scripts\Activate.ps1`).

FastAPI generates interactive API docs at <http://localhost:8000/docs> (Swagger UI) and <http://localhost:8000/redoc>.

The database URL is read from `DATABASE_URL_PY` (default `postgresql://postgres:postgres@localhost:5432/energy_dashboard`). It is separate from Prisma's `DATABASE_URL` because psycopg does not accept the `?schema=public` suffix.

**Differences from Express:** a `POST /api/energy/scenarios` with incomplete `kpis` (any of the three KPI numbers missing) returns `400` instead of being accepted, and malformed JSON returns the JSON error shape instead of an HTML error page.

## AI Agent (Chat + Optimizer)

*Branch: `feature/ai-agent-integration` (Express backend only; the FastAPI port does not include `/api/chat`)*

The dashboard ships with a Groq-powered chat agent that can answer natural-language questions, run what-if scenarios, and find the optimal PV capacity — all by calling server-side tools that wrap the same business logic the UI uses.

### Setup

1. `git switch feature/ai-agent-integration`, then `npm install` in `server/` (adds `groq-sdk` and `zod`).
2. Create a free API key at [console.groq.com](https://console.groq.com).
3. Add it to `server/.env` (never commit this file):

   ```env
   GROQ_API_KEY=gsk_...
   ```

4. Restart the API server. The assistant panel on the dashboard will become usable. Without a key, `/api/chat` returns `503`.

### Architecture

```
User → ChatPanel.tsx → POST /api/chat → runAgent loop → Groq (Llama 3.3 70B)
                                               ↓ tool_calls
                                        tools.ts dispatch
                                               ↓
                             [Prisma | calculateScenario | optimizer | scenarioStore]
```

- The **LLM decides which tools to call**; the loop in `server/src/agent/runAgent.ts` executes them and feeds results back until the model produces a final answer (capped at 6 steps).
- Tool arguments are validated with **zod** before any handler runs.
- The optimizer itself is a **deterministic grid search** (`server/src/agent/optimizer.ts`), exposed as a tool — keeping expensive reasoning in fast, reliable code while the LLM handles intent and explanation.

### Tools the agent can call

| Tool                | Purpose                                                              |
| ------------------- | -------------------------------------------------------------------- |
| `getEnergyData`     | Return the seeded 7-day baseline + KPIs                              |
| `calculateScenario` | Simulate KPIs for a specific `pvKw`                                  |
| `optimizeScenario`  | Grid-search best `pvKw` for `co2` / `coverage` / `minConsumption`    |
| `listScenarios`     | Read the in-memory saved-scenarios store                             |
| `saveScenario`      | Compute KPIs from the canonical baseline and persist the scenario    |

### Example prompts

- *"What was the average daily PV coverage?"*
- *"What would the KPIs look like if PV were 40 kW?"*
- *"Find the best PV size to maximize CO2 savings under 50 kW."*
- *"Save a 25 kW scenario."*

## API Reference

| Method | Endpoint                | Description                                                          | Express | FastAPI |
| ------ | ----------------------- | -------------------------------------------------------------------- | ------- | ------- |
| `GET`  | `/health`               | Health check                                                         | ✓       | ✓       |
| `GET`  | `/api/energy`           | Fetch the full energy dataset (timestamps, baseline, scenario, KPIs) | ✓       | ✓       |
| `GET`  | `/api/energy/scenarios` | List all saved scenarios                                             | ✓       | ✓       |
| `POST` | `/api/energy/scenarios` | Save a new scenario (`{ pvKw: number, kpis: object }`)               | ✓       | ✓       |
| `POST` | `/api/chat`             | Run the AI agent on a conversation (`{ messages: ChatMessage[] }`)   | AI branch | –     |

Endpoint errors are returned as JSON with an `error` message, e.g. `{ "error": "No energy data. Run migrations and seed." }`.

## Scenario Calculation

The frontend calculates scenario values in `src/utils/calculateScenario.ts` using these assumptions:

| Constant              | Value      | Description                                     |
| --------------------- | ---------- | ----------------------------------------------- |
| Peak sun hours        | 4 h/day    | Used to derive hourly additional PV             |
| Self-consumption rate | 60%        | Share of PV generation that offsets consumption |
| CO₂ factor            | 0.4 kg/kWh | Grid emissions factor                           |

## Notes

- Saved scenarios are stored **in memory** on the server and reset on restart. Persisting them to the database is a natural next step.
- The seed script wipes existing `EnergyDataset` rows before inserting, so re-running it is safe.
- The frontend calls the API on its own origin (`window.location.origin`); in development the Vite proxy forwards `/api` to the backend set in `vite.config.ts`.
