# Energy Dashboard – Scenario Comparison

A full-stack web application for visualizing energy consumption and PV (photovoltaic) generation, with an interactive scenario configuration that lets you compare baseline vs. custom PV capacity setups in real time.

**This branch (`migration/express-to-fastapi`) adds a second backend in Python.** `server-py/` is a 1:1 port of the Express API to **FastAPI**: same endpoints, same JSON responses, same error messages. The React frontend works unchanged with either backend, and you pick one with a single line in `vite.config.ts`.

## Features

**Dashboard**

- **Time-series chart** — hourly baseline vs. scenario comparison for consumption and PV generation over a 7-day window, with a brush/zoom control
- **KPI cards** — live-recalculated total consumption (kWh), PV coverage (%), and CO₂ savings (t)
- **PV Configuration** — slider + numeric input (0–100 kW) to adjust PV capacity; changes are applied on demand
- **Save scenarios** — persist named scenarios via the API (in-memory, resets on restart); optimistic UI updates
- **Skeleton loading states & error boundaries** — graceful handling of slow or failed API calls

**New in this branch: FastAPI backend**

- **Second backend in Python** — FastAPI + psycopg with the same endpoints, JSON responses and error messages as Express (verified byte for byte against Express)
- **Switchable backends** — the Vite dev proxy sends `/api` to Express (port 4000) or FastAPI (port 8000)
- **Typed request validation** — Pydantic models mirror `shared/types.ts`; invalid bodies return `400 { "error": ... }`
- **Interactive API docs** — generated by FastAPI at `/docs` (Swagger UI) and `/redoc`
- **pytest test suite** — health, saving and listing scenarios, invalid bodies, and database errors

## Quick Start

1. Install the Node dependencies: `npm install` in the root and in `server/` (the Express server also owns the migrations and the seed script).
2. Start PostgreSQL and load the demo data: see [Seeding the Database](#seeding-the-database).
3. Pick a backend and start it together with the frontend: see [Running the App: Express or FastAPI](#running-the-app-express-or-fastapi).
4. Open <http://localhost:5173>.

## Backend Architecture

The Express backend follows a clear **separation of concerns** between two files:

| File | Responsibility |
| ---- | -------------- |
| `server/src/index.ts` | **Infrastructure** — creates the Express app, configures middleware (CORS, JSON parsing), sets the port, mounts routers, and starts the server |
| `server/src/routes/energy.ts` | **Application logic** — defines all route handlers, validates request data, reads from / writes to the database |

This separation means `index.ts` never contains business logic, and `energy.ts` never concerns itself with how the server is started or configured. Adding a new feature only requires creating a new router file and registering it in `index.ts` with a single `app.use(...)` line.

The FastAPI backend keeps everything in one file, `server-py/main.py`, organized in sections: configuration and CORS, Pydantic models, error handlers, and routes.

## Seeding the Database

The seed script (`server/prisma/seed.ts`) populates the `EnergyDataset` table with one week of mock hourly data (Jan 1–7, 2025) sourced from `mock-data/energy-2025-01-01-2025-01-07.json`.

Start the database and run the seed once after applying migrations. Both backends read the same database, so this is needed for FastAPI too. The migrate and seed scripts need `DATABASE_URL` in `server/.env`, e.g. `postgresql://postgres:postgres@localhost:5432/energy_dashboard?schema=public`.

```bash
docker compose up -d db
cd server
npm run db:migrate   # apply schema migrations
npm run db:seed      # load mock data into the database
```

**What it does:**
1. Reads the mock JSON file containing `timestamps`, `baseline`, `scenario`, and `kpis` arrays.
2. Clears any existing rows in `EnergyDataset` (safe to re-run).
3. Inserts a single `demo` dataset row that the `GET /api/energy` endpoint serves to the frontend.

> Without seeding, the `GET /api/energy` endpoint returns a `404` and the dashboard will show no data.

## Running the App: Express or FastAPI

The browser always talks to the Vite dev server (`http://localhost:5173`). Vite forwards every `/api` request to **one** backend, set by the proxy `target` in `vite.config.ts`:

```
Browser ──► Vite :5173 ──/api──► Express :4000   (target: http://localhost:4000)
                              └► FastAPI :8000   (target: http://localhost:8000)
```

| Backend | Port | Proxy target |
| ------- | ---- | ------------ |
| Express (`server/`) | 4000 | `http://localhost:4000` (current setting) |
| FastAPI (`server-py/`) | 8000 | `http://localhost:8000` |

Restart Vite after changing the target. Both backends read the same database and can run side by side (for example to compare responses), but the page only uses the one the proxy points to. Each backend can always be called directly, e.g. `curl http://localhost:8000/api/energy`.

**With Express**

```bash
npm run dev          # starts Vite + Express together
```

**With FastAPI** (set the target to `http://localhost:8000` first, then use two terminals; see the next section for the one-time Python setup)

```bash
cd server-py && source .venv/bin/activate && uvicorn main:app --reload
```
```bash
npm run dev:web      # starts only Vite
```

> `npm run dev` always starts Express. When the proxy points to FastAPI, use `npm run dev:web` instead.

## Python Backend (FastAPI)

`server-py/` is a 1:1 port of the Express API to Python (FastAPI + psycopg): same endpoints, same JSON responses, same error messages, so the React frontend works without changes. `GET /api/energy`, `/health` and the error responses were compared byte for byte against Express.

**Prerequisites:** Python 3.9+, and PostgreSQL running and seeded (see [Seeding the Database](#seeding-the-database)).

**Mac / Linux**

```bash
cd server-py
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload        # http://localhost:8000
pytest                           # run the tests
```

**Windows (PowerShell)**

```powershell
cd server-py
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn main:app --reload        # http://localhost:8000
pytest                           # run the tests
```

The virtual environment only needs to be created once per checkout (`.venv/` is git-ignored); after that, activate it in each new terminal (`source .venv/bin/activate` or `.venv\Scripts\Activate.ps1`). Run `deactivate` to leave it.

FastAPI generates interactive API docs at <http://localhost:8000/docs> (Swagger UI) and <http://localhost:8000/redoc>.

The database URL is read from `DATABASE_URL_PY` (default `postgresql://postgres:postgres@localhost:5432/energy_dashboard`). It is separate from Prisma's `DATABASE_URL` because psycopg does not accept the `?schema=public` suffix.

### Express vs. FastAPI at a glance

| Concern            | Express (`server/`)                           | FastAPI (`server-py/main.py`)                                         |
| ------------------ | --------------------------------------------- | --------------------------------------------------------------------- |
| Database access    | Prisma ORM (`prisma.energyDataset.findFirst`) | Plain SQL with psycopg; JSONB is decoded to Python lists and dicts    |
| Request validation | Manual `typeof` checks                        | Pydantic models (`NewScenario`, `Kpis`) with strict number types      |
| Invalid body       | `res.status(400).json({ error })`             | `RequestValidationError` handler → `400 { error }` (instead of `422`) |
| Other errors       | `res.status(...).json({ error })`             | `raise HTTPException(...)` + handler → `{ error }` (not `{ detail }`) |
| Types              | `shared/types.ts`                             | Pydantic models mirroring `shared/types.ts`                           |
| Scenario store     | In-memory array (`unshift`)                   | In-memory list (`insert(0, ...)`)                                     |
| API docs           | —                                             | Generated at `/docs` and `/redoc`                                     |

**Differences from Express:** a `POST /api/energy/scenarios` with incomplete `kpis` (any of the three KPI numbers missing) returns `400` instead of being accepted, and malformed JSON returns the JSON error shape instead of an HTML error page. The frontend always sends complete KPIs, so the app behaves the same.

## API Reference

Both backends implement the same endpoints.

| Method | Endpoint                | Description                                                          |
| ------ | ----------------------- | -------------------------------------------------------------------- |
| `GET`  | `/health`               | Health check (`{ "ok": true }`)                                      |
| `GET`  | `/api/energy`           | Fetch the full energy dataset (timestamps, baseline, scenario, KPIs) |
| `GET`  | `/api/energy/scenarios` | List all saved scenarios (newest first)                              |
| `POST` | `/api/energy/scenarios` | Save a new scenario (`{ pvKw: number, kpis: Kpis }`) → `201`         |

Errors are always JSON with an `error` message (the frontend reads `body.error`):

| Status | When                                      | Message                                                              |
| ------ | ----------------------------------------- | -------------------------------------------------------------------- |
| `400`  | Invalid `POST /api/energy/scenarios` body | `pvKw (number) and kpis (object) are required`                       |
| `404`  | `EnergyDataset` table is empty            | `No energy data. Run migrations and seed.`                           |
| `500`  | Database unreachable or query failed      | `Database error. Check DATABASE_URL and that PostgreSQL is running.` |

## Scenario Calculation

The frontend calculates scenario values in `src/utils/calculateScenario.ts` using these assumptions:

| Constant              | Value      | Description                                     |
| --------------------- | ---------- | ----------------------------------------------- |
| Peak sun hours        | 4 h/day    | Used to derive hourly additional PV             |
| Self-consumption rate | 60%        | Share of PV generation that offsets consumption |
| CO₂ factor            | 0.4 kg/kWh | Grid emissions factor                           |

## Notes

- Saved scenarios are stored **in memory** by whichever backend is running and reset on restart. They are not shared between Express and FastAPI. Persisting them to the database is a natural next step.
- The seed script wipes existing `EnergyDataset` rows before inserting, so re-running it is safe.
- The frontend calls the API on its own origin (`window.location.origin`); in development the Vite proxy forwards `/api` to the backend set in `vite.config.ts`.
