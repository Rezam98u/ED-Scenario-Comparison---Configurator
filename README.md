# Energy Dashboard – Scenario Comparison

A full-stack web application for visualizing energy consumption and PV (photovoltaic) generation, with an interactive scenario configuration that lets you compare baseline vs. custom PV capacity setups in real time.

**This branch (`migration/express-to-fastapi`) runs on a Python backend only.** The Express + Prisma backend from `main` has been fully migrated to **FastAPI** (`server-py/`): the energy API, the AI agent, the seed script and the database migrations (now Alembic). Express stays on `main`, so the two implementations can be compared across branches.

## Features

**Dashboard**

- **Time-series chart** — hourly baseline vs. scenario comparison for consumption and PV generation over a 7-day window, with a brush/zoom control
- **KPI cards** — live-recalculated total consumption (kWh), PV coverage (%), and CO₂ savings (t)
- **PV Configuration** — slider + numeric input (0–100 kW) to adjust PV capacity; changes are applied on demand
- **Analysis** — daily autarky and the average hourly profile (pandas)
- **Save scenarios** — persisted in PostgreSQL (`SavedScenario` table, survives restarts); optimistic UI updates
- **Skeleton loading states & error boundaries** — graceful handling of slow or failed API calls
- **AI Assistant (Groq)** — tool-calling chat agent that can query the dataset, run what-if scenarios, find the optimal PV size and save scenarios

**Backend (FastAPI)**

- **Real data** — PV generation from Open-Meteo weather data, consumption from the BDEW G0 standard load profile
- **Typed request validation** — Pydantic models mirror `shared/types.ts`; invalid bodies return `400 { "error": ... }`
- **Database migrations with Alembic**, plain SQL with psycopg (no ORM)
- **Interactive API docs** — generated by FastAPI at `/docs` (Swagger UI) and `/redoc`
- **pytest test suite** — endpoints, calculations, analysis, seed script and agent; no network or database needed

## Seeding the Database

This branch uses **real data** (the mock dataset is only used on `main`). The seed script, `server-py/import_open_meteo.py`, fills the `EnergyDataset` table with real hourly data, by default for Aug 1–7, 2026 in Düsseldorf (NRW). It calls the Open-Meteo API, so it needs internet access (no API key).

Start the database, create the tables with Alembic, then run the seed once (with the virtual environment active):

```bash
docker compose up -d db
cd server-py
alembic upgrade head          # create the tables
python import_open_meteo.py   # load real data into the database
```

> Without seeding, the `GET /api/energy` endpoint returns a `404` and the dashboard will show no data.

**Database set up by Prisma** (on `main`, or on this branch before the switch to Alembic): it already has the tables, so run `alembic stamp 0001` once and then `alembic upgrade head`.

### Where the data comes from

- **PV generation** — hourly global tilted irradiance from the [Open-Meteo historical weather API](https://open-meteo.com/en/docs/historical-weather-api) (no API key, data up to yesterday), converted with a simple performance-ratio model: `kWh = kWp × irradiance / 1000 × PR`.
- **Consumption** — the BDEW **G0** standard load profile (commercial), with seasons, Saturdays, Sundays and NRW public holidays, scaled so the calendar year adds up to `--annual-kwh`.

Pass flags to load a different period, place or system:

```bash
python import_open_meteo.py --start 2026-10-01 --end 2026-10-07 --kwp 10
```

| Flag | Default | Meaning |
| ---- | ------- | ------- |
| `--lat`, `--lon` | `51.2277`, `6.7735` | Location (Düsseldorf, NRW) |
| `--start`, `--end` | `2026-08-01`, `2026-08-07` | Inclusive UTC days |
| `--kwp` | `10` | Baseline PV system size |
| `--tilt`, `--azimuth` | `35`, `0` | Panel tilt; azimuth 0 = south, -90 = east, 90 = west |
| `--pr` | `0.85` | Performance ratio |
| `--annual-kwh` | `75000` | Yearly consumption the G0 profile is scaled to (≈ 1,430 kWh/week) |

The API serves the oldest `EnergyDataset` row, so the script replaces the existing rows (in one transaction; safe to re-run). The tests never call Open-Meteo: they use a snapshot of the default week in `server-py/tests/fixtures/baseline_2026-08-01_2026-08-07.json`. The most recent days come from weather models and are later corrected by Open-Meteo's reanalysis, so re-running the import a few days later can change them slightly.

## Running the App

The browser always talks to the Vite dev server (`http://localhost:5173`), which forwards `/api` requests to FastAPI (`vite.config.ts`):

```
Browser ──► Vite :5173 ──/api/*──► FastAPI :8000   (energy data, scenarios, analysis, AI agent)
```

```bash
npm run dev          # starts Vite + FastAPI together
```

`npm run dev:api` starts FastAPI on its own, using the Mac/Linux virtual environment path (`.venv/bin/python`). On Windows, run `npm run dev:web`, and start FastAPI in a second terminal with `uvicorn main:app --reload` in `server-py/` (virtual environment active).

FastAPI can always be called directly, e.g. `curl http://localhost:8000/api/energy`, and has interactive docs at <http://localhost:8000/docs>. Restart Vite after changing `vite.config.ts`.

> Without FastAPI the dashboard shows an error. Without a `GROQ_API_KEY` only the chat panel fails.

## API Reference

| Method | Endpoint                | Description                                                          |
| ------ | ----------------------- | -------------------------------------------------------------------- |
| `GET`  | `/health`               | Health check (`{ "ok": true }`)                                      |
| `GET`  | `/api/energy`           | Fetch the full energy dataset (timestamps, baseline, scenario, KPIs) |
| `POST` | `/api/energy/calculate` | Scenario for a PV size: body `{ pvKw }` → `{ scenario, kpis }`       |
| `GET`  | `/api/energy/analysis`  | Daily stats and hourly profile of the baseline                       |
| `GET`  | `/api/energy/scenarios` | List all saved scenarios (newest first)                              |
| `POST` | `/api/energy/scenarios` | Save a new scenario (`{ pvKw: number, kpis: Kpis }`) → `201`         |
| `POST` | `/api/chat`             | Run the AI agent on a conversation (`{ messages: ChatMessage[] }`)   |

Errors are always JSON with an `error` message (the frontend reads `body.error`, not FastAPI's default `detail`):

| Status | When                                      | Message                                                              |
| ------ | ----------------------------------------- | -------------------------------------------------------------------- |
| `400`  | Invalid `POST /api/energy/scenarios` body | `pvKw (number) and kpis (object) are required`                       |
| `400`  | Invalid `POST /api/energy/calculate` body | `pvKw (number) is required`                                          |
| `400`  | Negative `pvKw` in `/api/energy/calculate`| `PV capacity cannot be negative`                                     |
| `400`  | Invalid `POST /api/chat` body             | `Invalid request body`                                               |
| `404`  | `EnergyDataset` table is empty            | `No energy data. Run migrations and seed.`                           |
| `500`  | Database unreachable or query failed      | `Database error. Check DATABASE_URL and that PostgreSQL is running.` |
| `503`  | `/api/chat` without `GROQ_API_KEY`        | `GROQ_API_KEY is not configured on the server.`                      |

## Data Processing in Python

Both endpoints read the baseline from the database (same `404`/`500` errors as `GET /api/energy`). The logic lives in pure functions without FastAPI code, so it can be tested on its own.

**`POST /api/energy/calculate`** — `server-py/calculations.py`, an exact port of `src/utils/calculateScenario.ts`, including JS `Math.round` rounding (Python's `round()` rounds halves to even). The frontend calls it with TanStack Query, cached per `pvKw`.

`test_calculations.py` checks that Python returns exactly the same numbers as the TypeScript function for pvKw 0, 5, 10, 33.3 and 100. To regenerate the fixture, run from the repo root:

```bash
npx tsx server-py/tests/generate_parity_fixture.ts
```

**`GET /api/energy/analysis`** — pandas analysis of the baseline (`server-py/analysis.py`), shown in the "Analyse" section of the dashboard:

- `daily`: per day `date`, `consumption_kwh`, `pv_kwh`, `self_consumed_kwh` (per hour `min(consumption, pv)`) and `autarky_pct` (self-consumed / consumption × 100)
- `hourlyProfile`: average `consumption_kwh` and `pv_kwh` per hour of the day (0–23)
- `peakConsumptionHour`, `peakPvHour`: hour with the highest average

All days and hours are **UTC**, like the timestamps in the data.

### Scenario calculation assumptions

| Constant              | Value      | Description                                     |
| --------------------- | ---------- | ----------------------------------------------- |
| Peak sun hours        | 4 h/day    | Used to derive hourly additional PV             |
| Self-consumption rate | 60%        | Share of PV generation that offsets consumption |
| CO₂ factor            | 0.4 kg/kWh | Grid emissions factor                           |

## AI Agent (Chat + Optimizer)

The dashboard ships with a Groq-powered chat agent that can answer natural-language questions, run what-if scenarios, and find the optimal PV capacity — all by calling server-side tools that wrap the same business logic the UI uses.

### Setup

1. Create a free API key at [console.groq.com](https://console.groq.com).
2. Add it to `server-py/.env`:

   ```env
   GROQ_API_KEY=gsk_...
   ```

3. Restart FastAPI. The assistant panel on the dashboard will become usable.

The model is the `MODEL` constant in `server-py/agent.py`. Groq retires models over time; `llama-3.3-70b-versatile` is no longer offered, so pick a tool-calling model that your key lists (for example `openai/gpt-oss-120b`).

### Architecture

```
User → ChatPanel.tsx → POST /api/chat → run_agent loop (agent.py) → Groq (MODEL)
                                               ↓ tool_calls
                                        run_tool dispatch
                                               ↓
                         [store.py | calculate_scenario | optimizer.py]
```

- The **LLM decides which tools to call**; `run_agent` in `server-py/agent.py` executes them and feeds results back until the model produces a final answer (capped at 6 steps).
- Tool arguments are validated with **Pydantic** models before any handler runs; invalid arguments go back to the model as `{ "error": ... }` so it can try again.
- The optimizer itself is a **deterministic grid search** (`server-py/optimizer.py`), exposed as a tool — keeping expensive reasoning in fast, reliable code while the LLM handles intent and explanation.
- Saved scenarios live in the `SavedScenario` table, so the agent sees scenarios saved from the dashboard, and scenarios the agent saves appear in the dashboard list.

### Tools the agent can call

| Tool                | Purpose                                                              |
| ------------------- | -------------------------------------------------------------------- |
| `getEnergyData`     | Return the seeded 7-day baseline + KPIs                              |
| `calculateScenario` | Simulate KPIs for a specific `pvKw`                                  |
| `optimizeScenario`  | Grid-search best `pvKw` for `co2` / `coverage` / `minConsumption`    |
| `listScenarios`     | Read the saved scenarios from the `SavedScenario` table              |
| `saveScenario`      | Compute KPIs from the canonical baseline and persist the scenario    |

### Example prompts

- *"What was the average daily PV coverage?"*
- *"What would the KPIs look like if PV were 40 kW?"*
- *"Find the best PV size to maximize CO2 savings under 50 kW."*
- *"Save a 25 kW scenario."*

## Migrated from Express (`main`)

The FastAPI backend keeps the Express API contract: the same endpoints, JSON responses and error messages (`GET /api/energy`, `/health` and the error responses were compared byte for byte), so the React frontend did not need changes.

| Concern            | Express (on `main`)                           | FastAPI (this branch)                                                 |
| ------------------ | --------------------------------------------- | --------------------------------------------------------------------- |
| Database access    | Prisma ORM                                    | Plain SQL with psycopg (`store.py`); JSONB decoded to lists and dicts |
| Migrations         | Prisma migrate                                | Alembic (hand-written SQL, `server-py/migrations/`)                   |
| Request validation | Manual `typeof` checks, zod (agent)           | Pydantic models with strict number types                              |
| Invalid body       | `res.status(400).json({ error })`             | `RequestValidationError` handler → `400 { error }` (instead of `422`) |
| Other errors       | `res.status(...).json({ error })`             | `raise HTTPException(...)` + handler → `{ error }` (not `{ detail }`) |
| AI agent           | `groq-sdk` (TypeScript)                       | `groq` (Python), same tools and request/response shape                |
| API docs           | —                                             | Generated at `/docs` and `/redoc`                                     |

**Differences:** a `POST /api/energy/scenarios` with incomplete `kpis` returns `400` instead of being accepted, and malformed JSON returns the JSON error shape instead of an HTML error page. The frontend always sends complete KPIs, so the app behaves the same.
